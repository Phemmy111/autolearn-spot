# ALEX Architectural Audit Report

## Executive Summary

**CRITICAL FINDING**: ALEX is currently implemented as a rigid template-driven form wizard, NOT an AI automation expert.

The system operates on a fixed schema with predefined fields, uses deterministic keyword-based mapping as the primary logic, and treats AI as a fallback for filling gaps in a predetermined questionnaire. The AI does not independently reason about user requests, adapt plans, or make architectural decisions. It is primarily asked to:

1. Extract values from user text to fit into a fixed schema
2. Identify which fields in the fixed schema are missing
3. Map user answers to specific schema fields
4. Generate options for specific schema fields

This is fundamentally a **template-driven architecture** with AI-assisted form filling, not an AI-driven automation expert.

---

## 1. Executive Diagnosis

### Why ALEX Behaves Like a Rigid Wizard

The current implementation violates the intended product architecture in several fundamental ways:

**1. Fixed Schema Before AI Sees Request**
- The `AutomationSpec` interface defines ~50+ fixed fields (automationType, platform, domain, trigger, inputs, outputs, integrations, businessRules, aiConfig, humanApproval, errorHandling, persistence, schedule, security, observability, architecture, etc.)
- This schema exists BEFORE the AI ever sees the user's request
- The AI is not asked "what automation does this user need?" but "which of these 50 fields can you fill?"

**2. Deterministic Question Generation**
- Questions are generated by iterating through a fixed set of "blockers"
- Blockers are determined by checking which fields in the fixed schema are missing
- The AI is asked "identify missing fields" not "what information do you need?"
- Question text is generated by template: `I need to know: ${blocker.replace(/_/g, ' ')}`

**3. Field-Value Format Requirement**
- Users are required to answer in `field: value` format
- The system parses this format and maps to the fixed schema
- Natural language answers require AI mapping, which is treated as a "fallback"
- The interface exposes internal field names to users (outputs.destination, schedule.timezone, etc.)

**4. No Dynamic Planning**
- There is no "plan" object that evolves based on conversation
- The system does not reason about architecture, trade-offs, or alternatives
- It does not adapt when requirements change mid-conversation
- There is no brainstorming or exploration phase

**5. Conversation = Workflow State**
- The system treats conversation messages as equivalent to workflow state progression
- Every message is assumed to be "continuing the previous form"
- New request detection is heuristic and unreliable
- No separation between conversational context and automation state

## 2. Proven Bugs

### Bug 1: Singular/Plural Field Mismatch
**Evidence**: User answers `outputs.destination: Email` but blocker is `outputs.destinations`
**Root Cause**: AI blocker identification returns singular forms, but keyword mapping expects plural
**Status**: Recently patched with normalization, but reveals deeper architectural issue

### Bug 2: Infinite Loop on Same Question
**Evidence**: User answers same question repeatedly, system doesn't recognize resolution
**Root Cause**: Field normalization fails, or blocker list not properly updated after answer
**Status**: Symptom of template-driven architecture

### Bug 3: New Request Contamination
**Evidence**: "Create a content summarizer bot" shows previous automation's schedule
**Root Cause**: Existing build lookup by conversationId doesn't distinguish new requests from continuations
**Status**: Recently patched with `detectWorkflowContinuation()`, but heuristic-based

## 4. New Request Contamination

### Code Path: `workflow-manager-v2.ts` line 74

```typescript
const existingBuild = await ArtifactService.getActiveBuild(request.conversationId, request.userId)
```

### Problem
- Lookup is by `conversationId` only
- Does not check if the new message is semantically a new automation
- Does not check if the previous automation was completed
- Relies on heuristic `detectWorkflowContinuation()` to distinguish

### Detection Logic (line 170)
```typescript
private static detectWorkflowContinuation(content: string, build: ArtifactBuild): boolean {
  const lowerContent = content.toLowerCase()

  // Strong indicators of new request
  if (lowerContent.includes('create') || lowerContent.includes('build') ||
      lowerContent.includes('make') || lowerContent.includes('new')) {
    // But only if it mentions a different automation type
    const currentType = build.final_specification?.automationType || ''
    if (!lowerContent.includes(currentType)) {
      return false // New request
    }
  }

  // Default: treat as continuation
  return true
}
```

### Why This Fails
- "Create a lead capture bot" and "Create a content summarizer bot" both match "create"
- Both might be classified as "chatbot" or "workflow"
- Heuristic is brittle and misses many edge cases
- No semantic understanding of "this is a different automation"

## 5. AI Reasoning Audit

### Where AI Is Used

**1. Semantic Extraction** (`SemanticAnalyzer.extractSpecification`)
- **Prompt**: "Extract a complete automation specification from the user's request"
- **Context**: User request, attached files
- **Output**: JSON with fields matching the fixed schema
- **Purpose**: Fill the predetermined schema
- **Reasoning**: NONE - just extraction

**2. Answer Mapping** (`SemanticAnalyzer.mapAnswer`)
- **Prompt**: "Map the user's answer to the correct specification field"
- **Context**: Question context, user answer, current spec
- **Output**: `{ field: "spec.field.path", value: "extracted value" }`
- **Purpose**: Map answer to fixed schema field
- **Reasoning**: Minimal - just mapping

**3. Blocker Identification** (`IntelligenceAnalyzerV2.identifyBlockers`)
- **Prompt**: "Identify critical missing information (blockers) that MUST be asked"
- **Context**: Current spec state, known fields
- **Output**: `{ blockers: ["field.path.1", "field.path.2"] }`
- **Purpose**: Identify which fixed schema fields are missing
- **Reasoning**: NONE - just checking completeness

**4. Architecture Design** (`ArchitectureDesigner.design`)
- **Prompt**: "Design a platform-independent logical automation architecture"
- **Context**: Completed spec
- **Output**: Logical architecture with stages
- **Purpose**: Generate artifact from completed spec
- **Reasoning**: LIMITED - operates on completed spec, not dynamic planning

### Where AI Is NOT Used

**1. Understanding the User's Intent**
- Intent detection is keyword-based (`detectAutomationType`, `detectDomain`)
- No AI analysis of what the user actually wants

**2. Deciding What Questions to Ask**
- Questions are generated from fixed blocker list
- No AI decision about whether a question is necessary

**3. Recommending Platforms**
- Platform selection is hardcoded (`selectPlatform`)
- No AI reasoning about best platform for the use case

**4. Adapting to Changes**
- No mechanism to handle "actually, change X"
- No dynamic plan updates

**5. Brainstorming**
- No AI brainstorming or exploration
- No suggestion of alternatives

**6. Natural Language Interface**
- Users must use `field: value` format
- Natural language requires AI mapping fallback

### Conclusion
The AI is used as a **form-filling assistant**, not as an **automation expert**. It operates within the constraints of a fixed schema and predetermined workflow.

## 7. Conversation vs Workflow State

### Current Implementation

**Conversation**: Stored in `alex_messages` table
- role, content, file_ids, created_at
- Pure message history
- No workflow state embedded

**Workflow State**: Stored in `alex_artifact_builds` table
- final_specification (the spec object)
- _knownFields, _blockerFields (tracking arrays)
- status (collecting_requirements, designing_architecture, etc.)
- questions (array of asked questions)

### Problem: No Separation

**Evidence 1**: Conversation lookup by conversationId
```typescript
const existingBuild = await ArtifactService.getActiveBuild(request.conversationId, request.userId)
```
- Assumes 1 conversation = 1 workflow
- Cannot have multiple automations in one conversation
- Cannot have conversation without workflow

**Evidence 2**: Every message treated as workflow continuation
```typescript
const isContinuation = this.detectWorkflowContinuation(request.content, existingBuild)
```
- No conversational mode separate from workflow mode
- Cannot chat without triggering workflow logic
- Cannot clarify or brainstorm without affecting workflow state

**Evidence 3**: Question context stored in spec state
```typescript
specState.questionContext = lastQuestion.context
specState.currentQuestion = lastQuestion.question
```
- Workflow state bleeds into conversation context
- Cannot ask unrelated questions during workflow
- Cannot pause workflow and resume conversation

### Required Separation

**Conversation Should Be**:
- User messages
- Assistant messages
- Questions
- Answers
- Brainstorming
- Clarifications
- Changes of mind
- Recommendations
- Completely independent of automation state

**Workflow State Should Be**:
- Current plan
- Requirements
- Assumptions
- Decisions
- Platform
- Nodes
- Connections
- Validation
- Artifact
- Generation status
- Separate from conversation history

### Current Violation
The system treats them as the same thing. A conversation IS a workflow. This prevents:
- Multi-automation conversations
- Conversational exploration before committing to workflow
- Mid-workflow clarifications without affecting state
- Changing requirements mid-conversation

## 8. Target Architecture

### Design Principle
ALEX should behave like an AI automation expert, not a form wizard.

### Proposed Architecture

```
USER REQUEST
    ↓
AI CONVERSATIONAL UNDERSTANDING
    ├─ Intent analysis (what does user want?)
    ├─ Context extraction (what information is provided?)
    └─ Ambiguity detection (what's unclear?)
    ↓
AI REASONING & PLANNING
    ├─ Brainstorm (what are possible approaches?)
    ├─ Recommend (what's the best approach?)
    ├─ Plan (what are the steps?)
    └─ Decide (what questions, if any, are needed?)
    ↓
DYNAMIC QUESTION GENERATION
    ├─ AI decides if question is needed
    ├─ AI generates natural language question
    ├─ AI accepts natural language answers
    └─ AI updates plan based on answers
    ↓
PLAN EXECUTION
    ├─ Generate architecture dynamically
    ├─ Adapt to changes mid-execution
    ├─ Handle ambiguities
    └─ Generate artifact when ready
```

### Key Changes

**1. Remove Fixed Schema**
- Replace `AutomationSpec` with dynamic plan object
- Plan contains: intent, approach, steps, requirements, decisions
- Requirements are dynamically discovered, not predetermined

**2. AI-Driven Questioning**
- AI decides whether to ask a question
- AI generates natural language questions
- AI accepts natural language answers
- AI decides when enough information is gathered

**3. Conversational Interface**
- Users never see internal field names
- Users never use `field: value` format
- All interaction is natural language
- AI handles all mapping internally

**4. Dynamic Planning**
- Plan evolves based on conversation
- AI can propose alternatives
- AI can adapt to changes
- AI can backtrack and revise

**5. Separation of Concerns**
- Conversation is separate from workflow state
- Can explore without committing
- Can clarify without affecting state
- Can have multiple automations per conversation

### Implementation Approach

**Phase 1: AI-Driven Questioning**
- Replace blocker identification with AI decision-making
- AI analyzes spec and decides "what do I need to know?"
- AI generates natural language questions
- AI accepts natural language answers

**Phase 2: Dynamic Planning**
- Introduce plan object separate from spec
- AI reasons about approach and steps
- Plan evolves based on conversation
- Can propose alternatives and adapt

**Phase 3: Conversational Interface**
- Remove `field: value` requirement
- AI handles all extraction and mapping
- Users never see internal fields
- Pure natural language interface

**Phase 4: Remove Fixed Schema**
- Gradually deprecate fixed schema
- Move to dynamic requirements
- Requirements discovered by AI
- Architecture generated from plan, not schema

## 12. Brutal Assessment

### Is the Current Architecture Fundamentally Capable?

**NO.**

The current architecture is fundamentally a template-driven form wizard with AI-assisted form filling. It is not designed to be an AI automation expert.

### Can It Be Evolved?

**YES, but requires significant architectural changes.**

The core components (artifact generation, architecture design, platform capabilities) can be salvaged. But the workflow management, state tracking, and question generation need to be redesigned.

### What Must Be Thrown Away?

1. **Fixed Schema**: The 50+ field AutomationSpec must be replaced with dynamic planning
2. **Blocker List**: The predetermined question list must be replaced with AI decision-making
3. **Field:Value Format**: The internal field exposure must be removed
4. **Keyword Classification**: The rule-based classification must be replaced with AI understanding
5. **Conversation=Workflow**: The coupling must be broken

### What Can Be Salvaged?

1. **Artifact Generation**: The actual workflow generation logic is solid
2. **Architecture Designer**: Can be used for plan execution
3. **Platform Capabilities**: The platform registry is valuable
4. **Database Schema**: Can be adapted for new architecture
5. **Frontend Components**: Can be reused with new backend

### Bottom Line

The current implementation does not match the product vision. It is a sophisticated form wizard, not an AI automation expert. Significant architectural redesign is required to achieve the intended behavior.

However, the components are well-built and can be reused. The path forward is clear: gradual migration from template-driven to AI-driven architecture, starting with AI decision-making for questions.
